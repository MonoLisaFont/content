# Mailrelay ownership sync and Black Week 2026 segmentation

Keep **Customers (group 1)** and **Prospects (group 3)** as separate Mailrelay lists. A subscriber in either list has one `monolisatier` field, including when they belong to both lists. Backfill that field from Juho’s Paddle Classic Transactions CSV, then have the website’s signed Paddle webhook maintain it on purchases and refunds. The field determines which Black Week draft a subscriber receives. [Website issue #1185](https://github.com/MonoLisaFont/website/issues/1185)

## Which value to store

Under **Subscribers → Custom fields**, create **MonoLisa tier** with tag name `monolisatier`, field type **Select**, and the options below. Use `unknown` as the default. Calculate the value from all active orders associated with a person and write that value to each of their verified subscriber records. [Custom field types](https://help.mailrelay.com/en/support/solutions/articles/103000425364) · [Select field and predefined options](https://apidocs.mailrelay.com/tag/custom-fields/POST/custom_fields)

Use the first matching row. For the personal upgrade emails, v1 and v2 each have one value because all editions of that version receive the same draft. Where someone owns both versions, use v2 for the email. My Orders determines the actual offer from the individual orders. It treats Code and Text as complementary families and Creator as a separate commercial license. Giving commercial ownership precedence here keeps mixed personal/commercial owners out of this campaign. [Website upgrade rules](../../../website/shared/canUpgrade.ts) · [Production product IDs](../../../website/shared/product_ids.ts)

| --- | --- | --- |
| `unknown` | Ownership or identity still needs verification | None |

| `v3_code_text` | Developer + Text bundle `925532`, or both standalone Code `925531` and Text `926417` | None |

## 1. Backfill existing subscribers from the Paddle CSV

1. **Read all versions and dates.** Use the Transactions export with customer email, order ID, product ID and order status. Record its cutoff. Include zero-value Trial orders and completed free upgrades. Reuse the existing backfill’s CSV parser and dry run. Its June 16, 2026 cutoff and Paddle Audience consent check apply to enrollment in group 1. An ownership backfill also covers earlier purchases and subscribers who joined through the website. [Transactions report](https://www.paddle.com/help/manage/reporting/a-comprehensive-insight-into-the-transactions-report) · [Checkout enrollment backfill](../../../website/docs/mailrelay-customers.md)
2. **Calculate the tier from active orders.** Count completed and partially refunded orders. Remove fully refunded or disputed orders and deleted subscriptions, then classify from what remains. If the export omits refund or subscription status, resolve the affected orders before assigning their tier. Match refunds by order ID and include known manual invoices. A v2 Complete owner eligible for a free upgrade stays at `v2` until they acquire v3. [Refunds report](https://www.paddle.com/help/manage/reporting/understanding-the-refunds-report) · [Website entitlement rules](../../../website/app/orders/orderEntitlements.ts)
3. **Match existing subscribers across both lists.** Read every page for groups 1 and 3, keeping the subscriber ID and existing memberships. Combine the two sets by subscriber ID before matching to Paddle by trimmed, lowercased email. Combine different addresses only through a verified account link. Report unmatched Paddle addresses and leave them out of the import. Use `none` for a subscriber with no order in the complete history and `unknown` for an unresolved match. Keep customer exports outside Git. [Subscriber lookup](https://apidocs.mailrelay.com/tag/subscribers/GET/subscribers)
4. **Update each subscriber once.** Preview counts for group 1 only, group 3 only and both, alongside the proposed tier changes. Prepare one row per changed subscriber, with email and tier. The CSV wizard adds every row to its selected destination groups. Import group 1 members (including overlaps) into group 1, then import group-3-only members into group 3. For each batch, select its single destination, enable **Update existing subscriber data** and choose **Keep current groups**. Read back the tier and compare membership and status with the pre-import records. [Mailrelay custom-field import](https://help.mailrelay.com/en/support/solutions/articles/103000236461-custom-fields-and-campaign-segmentation)

## 2. Keep the tier current from the website webhook

On a verified production checkout, including a free Trial or upgrade, look up the subscriber by exact email and check membership in either group 1 or group 3. Write the tier once per matching subscriber regardless of the checkout’s `marketing_consent` value. For example, someone in group 3 who buys Code with the checkbox empty stays in group 3 and gets `v3_code`. A subscriber already in both groups keeps both memberships. If checkout consent enrolls someone in group 1 through the existing flow, complete enrollment before updating their tier. Otherwise skip absent subscribers and those outside the two lists. Tier updates preserve status, suppressions, groups and consent evidence. [Paddle webhook](../../../website/app/api/webhooks/paddle/route.ts) · [Existing exact-email lookup](../../../website/utils/mailrelaySignup.ts) · [Enrollment client](../../../website/utils/mailrelay.ts)

Use the same classifier as the CSV backfill for purchases and refunds. Buying Text after Code yields `v3_code_text`. Fully refunding Text returns that owner to `v3_code` if Code is their only remaining entitlement. Read all pages of active order history and let Paddle retry transient failures. Repeated or overlapping alerts must converge on current ownership. The current Classic client reads a single page of up to 15 transactions. [Classic transaction client](../../../website/utils/paddle-api/index.ts)

Verify the tier write on a test subscriber before wiring it into checkout. Mailrelay documents mapped imports for custom fields. Its public subscriber PATCH schema lists `custom_fields` in the response and omits a write format for it. Confirm a field-only update that preserves status, groups and unrelated fields. Catch up purchases and refunds between the export cutoff and webhook activation using current ownership, so an older CSV value cannot overwrite a newer purchase. Reconcile before campaigns for disputes, missed events and buyers who subscribed after checkout. [Subscriber update](https://apidocs.mailrelay.com/tag/subscribers/PATCH/subscribers/%7Bid%7D) · [Import API](https://apidocs.mailrelay.com/tag/imports/POST/imports)

## Decisions from website issue #1185

- **Field and segments.** Use groups 1 and 3 for the current newsletter audience. Issue #1185 identifies group 5 as a separate website welcome group. A group-5-only contact is outside this rollout. Within the two lists, use `none` and `trial` for a general prospect audience. Paid owners have `v1`, `v2`, `v3_code`, `v3_text`, `v3_code_text` or `commercial`. Hold `unknown` out of both. [Mailrelay segment conditions](https://help.mailrelay.com/en/support/solutions/articles/103000156746-segmentations)
- **Refunds.** Use the remaining active licenses. A full refund of someone’s last paid order can return them to `trial` or `none`. A partial refund retains that order’s entitlement.
- **Privacy notice.** The published policy describes Paddle for online sales. It does not explicitly describe using license ownership to tailor newsletters. Suggested wording for the privacy review follows. “If you subscribe to the MonoLisa newsletter, we use the MonoLisa licenses you own to send relevant product and upgrade offers.” Consent evidence is tracked separately in #1168, and newsletter signup can proceed independently. [Published privacy policy](https://www.iubenda.com/privacy-policy/25140137/legal) · [Privacy review #1166](https://github.com/MonoLisaFont/website/pull/1166) · [Consent evidence #1168](https://github.com/MonoLisaFont/website/issues/1168)

## Verify and send once

Build four Black Week segments across the two lists. Each uses **(group 1 OR group 3) AND eligible for newsletter delivery AND tier equals the draft’s value**. In Mailrelay, use **Match any** for the two membership conditions and **Match all** between membership and the other filters. Trial setup tips alone do not confer newsletter consent. [Mailrelay segment conditions](https://help.mailrelay.com/en/support/solutions/articles/103000156746-segmentations)

Keep one private campaign roster across both lists with one row per person, selected subscriber ID and address, frozen draft and delivery status. For verified aliases, prefer the designated newsletter address, then the latest explicit opt-in, then the lowest subscriber ID. Hold conflicting identities or consent. Someone in both groups who owns v2 appears once on the v2 delivery list. [Mailrelay sending guide](https://help.mailrelay.com/en/support/solutions/articles/103000424825)

- **Freeze the four delivery lists before the first send.** Save each segment as a static campaign group and reconcile its members to exactly the selected subscriber IDs on the roster. Remove alternate addresses. All six pairwise intersections must be empty by person key, subscriber ID and normalized address. The sum of group sizes must equal the number of distinct assigned people. Select only the corresponding static group when preparing each delivery. [Mailrelay segment and group behavior](https://help.mailrelay.com/en/support/solutions/articles/103000156746)
- **Spot-check overlaps.** Trial + v1 + v2 gets the v2 email. V2 + v3 Code gets the v3 Code email. Code + Text bought separately gets no email, including when a verified alias holds the second purchase. V2 + standalone v3 Text gets no email. A newsletter subscriber with only a legacy trial gets the Trial email. A trial-tips-only contact gets no email.
- **Recheck eligibility before each delivery.** Remove anyone who has unsubscribed, changed tier or otherwise ceased to qualify for their assigned copy. Compare the final preview with the roster after suppressions. A Trial recipient who buys Code between sends stays out of the v3 Code delivery even though the ownership field now reads `v3_code`.
- **Reserve once across all four sends.** Use one sending operator and one roster for `black-week-2026`. At launch or restart, reconcile any existing Black Week deliveries under **Reports → Sent campaigns**. Before submitting each variant, reserve its recipients in the roster. Save the Mailrelay delivery ID when scheduling or queueing succeeds. Anyone already reserved, scheduled, queued or sent is ineligible for another delivery in this campaign.
- **Recover the original delivery on a retry.** After a timeout, pause or partial failure, look up the recorded delivery and resume it where possible. A replacement send may include only people confirmed never queued in any of the four deliveries. Hold uncertain rows and use delivery records to reconcile them. Opens and clicks cannot establish who was queued. [Sending and delivery reports](https://help.mailrelay.com/en/support/solutions/articles/103000424825)

## Future Text-only campaign

For a future offer to add Code, select newsletter subscribers where **MonoLisa tier** equals `v3_text`. Someone who owns v2 and standalone v3 Text belongs to this audience. Once they also buy v3 Code, their value becomes `v3_code_text` and they leave the Text-only segment. [My Orders upgrade paths](../../../website/shared/canUpgrade.ts)
